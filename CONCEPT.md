# Mycel: memory of the product concept

Recorded on 27 October 2026. This document describes the idea and the user's latest requirements. The state of the implementation is described separately in [PROJECT_STATE.md](PROJECT_STATE.md).

## The problem

When an AI agent builds a product, the whole picture often lives only in the agent's context. As features appear and stages are completed, the product's logic, vision and progress change. It is hard for a person to see these changes and to think the whole system through together with the agent.

A shared map of the product is needed, available to both the person and the agent. It should show what is being built, how it works, what parts it consists of and which decisions are still open.

## Product format

A small repository with a service that runs locally. The person works with the map in a browser; Codex, Claude or another agent reads and changes it through requests to the local server.

It is a workspace for designing a product together: you can change the logic, think scenarios through, break large parts into smaller ones, record questions and track progress.

At first the user suggested a mind map as a possible form, but no specific library or way of drawing was agreed. The working model is nested blocks with directed links.

## How the map works now

A free canvas. A block is a card with a title, text, position, size and colour. A block can contain a sub-map: nested blocks and notes with coordinates relative to its field. A block that gets a sub-map immediately gets a roomy field, a canvas inside the block; blocks in it move freely and can be dragged into and out of the sub-map, and the field grows when it gets crowded and remembers its size. A collapsed sub-map is a compact card with the block's header and the number of blocks and notes inside; when it is expanded, its neighbours move apart, and when it is collapsed, they come back. An expanded sub-map is a calm area with a thin outline; if there are marks inside, a readiness strip runs along its top edge. From far away, cards show only large titles. Nesting sets the levels of abstraction: the main map is the concept, its sub-maps are mechanics (both short and in simple words for a person who does not program), below that is the technical level for developers, and lower still is code; the slider in the bottom bar shows the map down to the chosen level. Double-clicking a block with a sub-map dives into it: the map shows only that block and one level below it, with the path at the top; Esc or double-clicking empty space goes up one level. Double-clicking a block without a sub-map, or a note, edits it; any block can also be edited with the pencil in its corner. The map takes the full width; below it, as in n8n, is the control bar (tabs, levels, the agent's dot, download), and above the bar is what the agent is doing right now. There is no chat: people talk to the agent in its own window; when the agent shows a block, the map moves to it. While the person is editing the map, "Finish edits" with the number of records is at the bottom centre of the map. Block marks are shown with the border: plan is dashed (logic without finished code), testing pulses, passed is green, failed is red (and so is a sub-map with such a block inside); a mark change flashes. An agent proposal is highlighted: new things are dashed, things to be deleted are faded and struck through; at the bottom centre are its title, "Reject" and "Accept". The look is calm, without an "AI" feel: the agent is a green dot, with no explanatory labels. A note is a sticker with text, free or attached to a block: an attached note moves with the block and is deleted with it. A link is a directed line between two blocks with an optional label. Blocks and notes are created through the right-click context menu (on empty space, a block or a note; on a block, a note on it), moved by dragging and resized by the corner; a link is created by dragging from any edge of a block (or from the circle on the edge, or with Alt from anywhere on the block) to anywhere on another block, including a block lying behind; dropping on empty space creates nothing. The map background has no dots.

## What the map stores

Model version 3:

- Node: a stable ID, a type (block or note), a level (the main map or a container block), for a note the block on the same level it is attached to, for a block whether its sub-map is collapsed, a title, text, x and y coordinates relative to the level, width and height, a colour from a small palette; a block has a mark (plan, passed, failed), and a node or link in an open proposal has a flag (add, change, remove).
- An open agent proposal: its title, whose it is, when it was made and the previous content of the nodes and links it changed, so that rejecting it restores the map.
- Link: source block, target block, label.
- History: revision, author, time, reason and summary of the change, and a delta: which nodes and links were added, changed (with field names) and deleted.

Maps of earlier versions (nested blocks with essence, logic, criteria, questions and status fields) are converted into free ones: nesting becomes parent → child links, the fields are gathered into the block's text, and the blocks are arranged as a tree from left to right. The original file is kept next to it as a backup.

## How the agent works

One app on `127.0.0.1:4317` keeps all projects in `.mycel/` next to the program. The agent is given the `/agent` address with the guide and the Mycel command for this computer, connects the project folder (`mycel.mjs init`: the same folder is the same project, otherwise a new one, which immediately appears on the person's home page), and from then on `mycel.mjs` finds the project by its folder and starts Mycel itself if it is not running. The agent builds an empty map as it reads the code (the concepts, then the mechanics of each), and `build` writes in steps, so the person sees the map grow; the view follows the new blocks until the person moves the map themselves. The agent does not reconnect a project the person has deleted. The agent works through `mycel.mjs` (or directly through the HTTP API): it reads the whole map in Markdown or JSON, and the revision it has read is remembered separately for each agent. After that it learns what others changed since it read the map: on request (`changes`) or by waiting (`wait`), which ends at the first content edit by someone else; moves and size changes arrive together with it, but on their own do not wake the agent (the user's decision); in Claude Code the wait runs in the background, and its end reaches the agent as a notification. The agent's own edits do not wake it. The agent builds a whole structure as a tree (`build`): blocks with sub-maps, notes and links without coordinates, and the server places them itself. Writes only go on top of the revision that was read: if the map has changed in the meantime, the agent gets the changes instead of writing. The person talks to the agent in the agent's window; Mycel has no chat; the agent sees what the person has selected and which block they are working in, shows them what it is doing right now (`doing`) and the block it is talking about (`show`), and the interface shows with a dot whether it is connected. Agents work through `mycel.mjs` or the MCP server `mcp.mjs` with the same commands. The person hands over their map edits as a batch: until they press "Finish edits", the agent does not wake on them. Logic changes the person has not yet approved are not written by the agent straight away but proposed (`propose`); the person's decision reaches it in `wait` and `changes`. After tests the agent marks blocks green or red (`mark`). Agents' edits are visible on the map at once and in History with the agent's name. When building the map, the agent lays it out on four levels: concept and mechanics short and in simple words for a person who does not program, technical with components, files, libraries and technical risks, and code with steps, functions and files. `mycel.mjs` does not write an agent batch that has code, files, names from code or long text on the concept and mechanics levels, and names what to move to the technical level.

## Implementation principles

- Simple local launch and a small repository.
- Shared data for the browser and agents.
- Explicit changes with a clear reason.
- Protection against overwriting concurrent edits.
- Data stays safe across restarts.
- The product can be developed on the map without being tied to the implementation.

Node.js without external dependencies, JSON on disk, REST and SSE are decisions already made for the MVP, not the user's original constraints.

## Not in the current scope yet

Mandatory block fields and changing marks by hand in the interface (the agent sets marks); automatic code analysis (the agent names the files for blocks; Mycel only searches them for TODO markers and things that look like keys); the hub running checks itself; cloud hosting; authorisation of several users; pushing events straight into the agent's session (Claude Code channels are an experimental, terminal-only feature). Import, undo for all actions (currently only deleting a block, a note or a link can be undone), multi-select and laying out existing blocks remain possible directions, not an agreed work plan; only blocks the agent added without coordinates are placed automatically.
