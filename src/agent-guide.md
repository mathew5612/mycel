# Mycel: инструкция для агента

Mycel — общая карта проекта. Человек смотрит её в браузере ({{url}}) и видит твои правки сразу. Прочитай эту
страницу целиком через командную строку (`curl.exe -s {{url}}/agent` в Windows, `curl -s {{url}}/agent` в других
системах) или командой `guide` ниже, а не пересказом.

Чата в Mycel нет: человек говорит с тобой в твоём окне (Claude Code, Codex), и отвечаешь ты там же. Mycel — карта,
которую вы оба видите, и кнопки человека на ней: «Закончить правки», «Принять» и «Отклонить» у твоего предложения.
{{remote}}
Команда Mycel:
- PowerShell: `& {{command}} <команда>`
- bash: `{{command}} <команда>`

Ниже `mycel` — эта команда. Запускай её из корня проекта, над которым работаешь. Claude Code подписывается как claude
сам, другой агент добавляет `--actor <имя>`. В песочнице без сети запускай команды Mycel с разрешением на сеть.

Плагин Mycel — обязательно, это первый шаг. Человек, который ведёт Mycel, работает с агентами только через него:
плагин даёт инструменты `mycel_*` (MCP), подписывает на карте блоки файлов, которые ты правишь, в конце ответа
напоминает обновить их описание, а в начале каждой сессии даёт обзор карты.
- Есть инструменты `mycel_*` — плагин стоит. Пользуйся ими вместо команды: `mycel_context` вместо `mycel context`,
  пакеты для `mycel_apply`, `mycel_build`, `mycel_propose` — объектом, без файлов.
- Нет их, а ты — Claude Code: выполни `mycel plugin --install` (подключает плагин и убирает отдельно подключённый
  MCP-сервер mycel; повторно — безопасно) и скажи человеку начать новую сессию: инструменты и хуки появятся в ней.
  Если команда не нашла claude, она напечатает две команды `claude plugin …` — выполни их. До новой сессии работай
  командой `mycel`.
- Другой агент — тот же MCP-сервер Mycel: `mycel plugin --agent <имя>` печатает запись и файл настроек, куда её
  добавить к остальным серверам (codex, cursor, antigravity, gemini, vscode, windsurf, cline, claude-desktop и клиенты
  локальных моделей: lmstudio, continue, goose, opencode, jan, openwebui); подключи и начни новую сессию. У Codex и
  Cursor запись включает и хуки Mycel. У остальных хуков нет: запусти в фоне `mycel watch` в папке проекта —
  изменённые файлы отмечаются сами, — или после правки файлов вызывай `mycel_touch`; перед концом работы обнови
  описание блоков или `mycel_fresh`.
- Агенту без MCP хватит команды `mycel`: `mycel tools` — описания всех инструментов для вызова функций (формат
  OpenAI), `mycel call <инструмент> '<json>'` — вызов. Своя локальная модель без клиента (Ollama, LM Studio,
  llama.cpp) — `mycel chat --model <имя>`: Mycel сам даёт ей инструменты, короткую инструкцию и чтение файлов проекта.

Подключение:
- `mycel init` — из корня проекта. Корень — ближайшая папка с `.git` (в git worktree — основной репозиторий); если
  `.git` нет нигде выше, корень — сама папка, из которой запущена команда. Если эта папка уже подключена,
  используется её проект с картой; если ты в подпапке подключённого проекта — тот проект; иначе появится
  новый проект, и человек сразу увидит его на главной странице. Своё название — `--name 'Название'`; у уже
  подключённой папки `--name` переименовывает проект — только по просьбе человека.
- `mycel projects` — все проекты. Если твой проект показан с пометкой «папки нет» (папку перенесли или
  переименовали), подключи его к текущей папке: `mycel init --project <id>`.
- Если команда сообщает, что проект удалён человеком, остановись и не подключай его заново, пока человек не попросит
  (`mycel init --new`).

Перед задачей:
- Прочитай карту: `mycel context`. Там все блоки с полным текстом и уровнем, вложенность (подкарты), заметки, связи
  с их id, что человек выделил и в каком блоке работает. Только смысл, без координат и размеров: `mycel context --brief`.
- Человек пишет «сделай это», «вот этот блок» — смотри `mycel selection`: что он выделил на карте и в каком блоке
  работает, с полным текстом.
- Если Mycel недоступен, сообщи об этом; не утверждай, что карта актуальна.

Уровни карты задаются вложенностью. Концепцию и механику читает человек, который не программирует: по ним он
понимает, что есть что, и ставит задачи. Технику и код читают разработчики.
- Концепция — блоки основной карты: что это за часть и зачем она пользователю продукта. Название — 1–3 простых слова,
  текст — одно короткое предложение. Хорошо: «Корзина» — «Покупатель собирает товары перед оплатой». Плохо:
  «CartService» — «`cart.ts` хранит позиции в Redis».
- Механика — подкарта концепции: как эта часть работает, шагами и частями, понятными без программирования. Название —
  1–4 слова, текст — одно предложение, связи подписаны простыми словами («товар», «сумма»). Хорошо: «Покупатель
  кладёт товар» → «Корзина считает сумму». Плохо: «addItem и редьюсер» — «`useCart()` отправляет ADD_ITEM».
- Техника — подкарта механики: как это устроено — компоненты, файлы, библиотеки, сервисы, настройки, данные. Файлы и
  библиотеки в `обратных кавычках`, 1–3 коротких предложения. Хорошо: «Хранилище корзины» — «`cart/store.ts` держит
  позиции в Redis по id сессии». Плохо: пересказ механики без файлов.
- Код — подкарта техники: шаги в порядке выполнения. Название — действие («Проверить остаток»), в тексте функция и
  файл, ключевые параметры: `checkStock(sku, qty)` в `cart/stock.ts`. Плохо: «Шаг 2» — «Дальше вызывается проверка».
- На концепции и механике нет кода: обратных кавычек, вызовов `name()`, имён файлов и путей, имён вроде `BOT_TOKEN`,
  `handle_message`, `getResponse`, жаргона («диспетчер», «polling», «callback», «API-клиент»). Названия, которые знает
  обычный человек (Telegram, OpenAI, PDF), — можно. Ориентир: название до 30 символов, текст до 120.
- У каждого блока механики — подкарта техники, хотя бы блок с файлами и компонентами, которые её делают. Код — там,
  где несколько осмысленных шагов (основные потоки); часть из одной функции — функция и файл в тексте блока техники.
- Проблему пиши дважды: на механике — заметкой простыми словами («Если прислать фото, бот молчит»), на технике или
  коде — заметкой с причиной (у фото нет `message.text`, и проверка команды падает).
- Типы и структуры данных называй в подписях связей техники или в заметке. Тесты — концепция «Проверка» или заметки
  к блокам, которые они проверяют. Несвязанные части продукта — отдельными группами с заметкой.
- Связывай блоки одного уровня: стрелка от одной части к другой, а не к блоку внутри её подкарты, — чтобы было видно,
  что за чем идёт. Внутри подкарты связывай её блоки между собой.

Первая карта: если карта пустая, построй карту проекта по ходу чтения, чтобы человек видел, как она растёт.
- Сначала обзор: дерево файлов, README, манифесты (package.json, pyproject.toml и т. п.), точки входа. Весь код подряд
  читать не нужно.
- Как только понятны концепции (обычно 4–8), сразу `mycel build <файл>` с ними и связями между ними.
- Затем по одной концепции: прочитай её код и одним `mycel build <файл>` с `"parent": "<id концепции>"` добавь её
  механику, внутри каждого блока механики — блоки техники, внутри техники основных потоков — шаги кода. Блоки
  встают сами, соседи раздвигаются.
- Шаги показывай через `mycel doing` («читаю `bot/`», «строю механику «Корзины»»), в конце — `mycel doing --done`
  и одна фраза человеку, что построено.
- Ориентир по расходу: проект на 40 файлов — около 200 тыс. токенов и 10 минут.

Отметки блоков — что из карты уже есть в коде и проверено:
- Пунктир (`plan`) — логика без готового кода: блок, которого ещё нет в коде или который не проверен после
  изменения. Блоки, созданные человеком на карте, сразу планом. Зелёная рамка (`passed`) — код написан и тесты прошли,
  красная (`failed`) — проверка не прошла, пульсирующая (`testing`) — проверка идёт сейчас. Блок без отметки — как
  раньше, например карта уже написанного кода.
- `mycel mark <id[,id…]> plan|testing|passed|failed|none`. Человек смотрит, как карта окрашивается по ходу тестов,
  поэтому: перед прогоном отметь проверяемые блоки `testing`; запускай тесты по блоку или небольшой группе (не
  одним прогоном всего в конце) и сразу после каждого отмечай итог — `passed` или `failed`. Шаги кода и выше — блок
  техники, механики, концепции — зелёным, когда всё внутри прошло. Упавшее — красным и заметкой с причиной на уровне
  техники или кода. Подкарта с проверяемым или красным внутри показывается так же сама.
- Добавляешь блок того, чего ещё нет в коде, — с `"status": "plan"` (в build и в add-node).

Код и карта — чтобы карта не устаревала:
- У блоков техники и кода указывай их файлы и команду проверки: в build и add-node — `"files": ["cart/total.ts",
  "cart/"]` (пути от корня проекта, папка — с `/` в конце) и `"test": "npm test -- cart"`. Команду `node …` Mycel
  запускает тем же node, что и себя.
- Меняешь файлы — их блоки помечаются «возможно устарел» (с плагином Mycel в Claude Code — сами, после каждой правки
  файла; иначе — `mycel touch <файл…>`), а человек видит над блоком твоё имя. Когда закончил: если устройство
  поменялось, обнови текст этих блоков (`apply`) — пометка снимется; если описание верно, подтверди: `mycel fresh
  <id[,id…]>`. Устаревшие блоки перечислены в context.
- Проверка — `mycel check [id[,id…]]`: запускает команды `test` у блоков и у вложенного в них, сама ставит `testing`,
  потом `passed` или `failed` по каждой команде — человек видит, как карта окрашивается. Человек может нажать
  «Проверить» у блока — это придёт в wait и changes: выполни check и скажи итог.
- Берёшься за блоки — `mycel doing '…' --on <id,…>`: человек и другие агенты видят, кто над чем работает. Если блок
  уже делает другой агент, команда скажет об этом — согласуй с человеком.
- Что изменилось в устройстве проекта, по концепциям, — `mycel review` (за сутки; `--hours N`, `--since ревизия`):
  в конце большой работы покажи человеку итог так. Где дыры — `mycel health`: красные, устаревшие, без проверки,
  план, TODO и похожее на ключи в файлах блоков (только файл и строка).
- Агент в виртуальной машине (VMware и др.) может работать с этой же картой. Доступ открывает `mycel remote on` — с согласия человека; `mycel remote` печатает команду установки для агента там (`curl -fsS http://<адрес>:4317/install.sh | sh`). Тот ставит всё сам и просит доступ, человек нажимает «Разрешить» в Mycel. Сам на запрос не отвечай: это решение человека.
- Плагин Claude Code (MCP, подсветка правок, напоминание обновить карту, обзор карты в начале сессии) собирает
  `mycel plugin`; ставит его человек — предложи, если плагина нет.

Предложение: изменения логики, которые человек ещё не утвердил (новая ветка, переделка механики, другой порядок
шагов), не пиши на карту сразу, а предложи: `mycel propose <файл>`. Файл — как у build (`"parent"`, `"blocks"`,
`"notes"`, `"links"`) и (или) `"operations"` как у apply, плюс `"title"` — название предложения:

```json
{ "title": "Промокоды в корзине", "parent": "korzina",
  "blocks": [ { "id": "promo", "title": "Промокод", "text": "Покупатель вводит код и получает скидку" } ],
  "links": [ ["promo", "summa", "скидка"] ],
  "operations": [ { "type": "update-node", "id": "summa", "patch": { "text": "Сумма считается со скидкой" } },
                  { "type": "delete-node", "id": "kladet" } ] }
```

- Новое ложится на карту пунктиром с подсветкой, изменённое подсвечивается, удаление только помечается; свёрнутые
  подкарты с предложенным раскрываются. В `context` у таких блоков «предложено: добавить / изменить / удалить».
- Скажи человеку одной фразой, что предлагаешь и зачем. Пока предложение открыто, человек правит его на карте, а ты —
  следующим `propose` (дополняет открытое) или `apply` по предложенным блокам.
- Принимает или отклоняет человек кнопками; решение приходит в `wait` и `changes` («принял предложение» с его
  правками или «отклонил»). Принятые блоки — план: если человек просил само изменение, реализуй их в коде, прогони тесты и отметь
  итог (`mark`). Отклонённое снято с карты, всё вернулось.

Фокус: если человек работает над одним блоком, в context и в изменениях будет строка «Человек в фокусе на …».
Тогда читай только его: `mycel context --focus <id>` — блок со всем вложенным и связи с остальной картой, и работай в
его рамках.

Пока работаешь:
- Узнавай о действиях человека в Mycel и правках карты. Если умеешь фоновые задачи (Claude Code), держи `mycel wait`
  в фоне (в MCP — `mycel_wait`: Claude Code сам уводит долгий вызов в фон): когда человек закончит правки, решит по
  твоему предложению или кто-то изменит содержимое карты, ожидание завершится и пришлёт это; учти и запусти снова.
  Иначе вызывай `mycel changes` в начале каждого шага.
- Изменения приходят с текущим текстом блоков; твои собственные правки в них не попадают. Перемещения и размеры не
  будят, а приходят вместе со следующей правкой.
- Человек правит карту пачкой: с его первой правки у него внизу кнопка «Закончить правки», и до её нажатия `wait` на
  его правки не просыпается, а `context` и `changes` пишут «Человек сейчас правит карту». Не отвечай на эти правки и
  не меняй то, что он правит. Нажатая кнопка приходит строкой «правки карты готовы» вместе с изменениями: учти их;
  если в них просьба (новый блок, заметка с вопросом), сделай и коротко скажи человеку, что сделал.
- Что делаешь сейчас — `mycel doing 'читаю `server.mjs`'` (с `--progress 40`, если знаешь долю): человек видит строку
  под картой. Не чаще раза на шаг; в конце — `mycel doing --done`.
- Показать человеку блок, о котором говоришь, — `mycel show <id>`: карта переходит к нему и выделяет его.
- Вывод `wait`, `changes` и `build` читай целиком, не обрезай его (`head`, `Select-Object -First`): напечатанное
  считается прочитанным и второй раз не придёт.

Кавычки: текст для doing бери в одинарные кавычки — в двойных PowerShell и bash ломают обратные кавычки. Апостроф
внутри пишется `''` в PowerShell и `'\''` в bash. Файлы для build, apply и propose пиши своим инструментом записи
файлов (UTF-8), не через Set-Content и не через конвейер, во временной папке вне проекта.

Как менять карту:
- Структура — `mycel build <файл>`: `{ "message", "parent" (id блока, необязательно), "blocks": [ { "id", "title",
  "text", "color", "status", "files", "test", "blocks": [ … ], "notes": [ "текст" ] } ], "notes": [ … ], "links":
  [ ["откуда", "куда", "подпись"] ] }`. id можно не указывать — он составится из названия; связь ссылается на id или однозначное название.
  Координаты не нужны: блоки встанут сами. Если build прервался, повтори его с тем же файлом: уже записанные блоки,
  заметки и связи пропускаются.
- Точечные правки — `mycel apply <файл>` с `{ "message", "operations": [ … ] }` (или просто массивом операций);
  причину можно дать через `-m`. id блоков и связей — из context (у связи — после `· id:`). Например, в механику
  корзины выше:

```json
{ "message": "Доставка в корзине", "operations": [
  { "type": "add-node", "node": { "id": "dostavka", "parentId": "korzina", "title": "Выбор доставки", "text": "Покупатель выбирает курьера или самовывоз" } },
```
